# 캡스톤 목표 재정의와 연구 설계 v2 (2026-11-10 초안)

정태웅 11/10 요구 3번("목표를 다시 생각해서 효과적이고 신뢰도 높은 연구와 결과를 얻게 설계")에 대한 안이다. 제품 구조는 `product-architecture-v2.md`, 측정 실험은 `security-impact-design.md`, 근거 조사는 `korea-ksa-research.md`·`security-software-survey.md`.

> **상태: 방향 확정(11/10 저녁, 정태웅), 세부는 초안.** 발표(12/11)까지 약 4주 반이다. 이 문서는 "무엇을 주장하고, 그 주장을 어떤 숫자로 뒷받침할지"를 먼저 정하고, 거기에 필요 없는 일은 빼는 것을 목표로 한다.
>
> **11/10 결정**
> 1. 목표 재정의(2절)에 동의. 참여자 데이터는 핵심 숫자에서 뺀다(0.8.1 암호 키 분실로 지금은 쓸 수 없음).
> 2. 영향 측정은 권장판으로 한다. 단 **중간에 사람 손이 필요 없도록 자동화를 먼저 완성하고, 측정은 그 뒤에** 한다(`security-impact-design.md` 11절).
> 3. 위험도 점수는 C# 라이브러리로 만든다.
> 4. 참여자 동의문의 AI 전송 항목은 다음 배포 때 넣는다. 그전에는 팀·검증 테스터 PC에서만 AI 기능을 쓴다.
> 5. API 키는 빌드에 넣되, 그 빌드는 검증 테스터와 평가자(교수·조교)에게만 준다. 서버는 예산 때문에 두지 않는다(`product-architecture-v2.md` 3.4).

> **11/11 결정(정태웅)**
> - **보안 프로그램 설치를 미룬다.** PC가 한 대라 설치 뒤에 만드는 사례에는 전부 보안 모듈이 섞인다. 설치 전에 깨끗한 상태의 사례 덤프(브라우저 부하, FaultLab, 재현 사례)를 먼저 만든다. 설치 전 측정(S0)의 남은 2블록은 설치와 무관하게 진행한다.
> - **Hyper-V를 켠다.** 가상 머신에서 보안 프로그램 설치 예행연습, 실행기 시험, Beta 설치·업데이트 시험을 한다(체크포인트로 되돌림). 켜면 호스트의 드라이버·서비스가 바뀌므로 **설치 전 측정은 시범부터 새 실험으로 다시 잰다.** 11/11 새벽의 자료(시범 3 + 설치 전 4블록)는 "Hyper-V 켜기 전" 자료로 보관한다. 측정 세션 중에는 가상 머신을 끈다(실행 중이면 세션이 시작을 거부).
> - **Beta는 PC 블랙박스 + 자동 업데이트부터** 팀에서 먼저 진행한다. UI는 준비되면 합친다. 11/11 확인: UI는 엔진과 이미 연결돼 있다(`EngineClient`). 연결되지 않은 것은 Claude API(연결 지점 `IChatAgent`와 오프라인 대역만 있음), PC 블랙박스 기록 폴더 감시(11/02에 빼서 보관), 저장소 밖에서 실행되는 배포 형태(지금은 저장소 폴더와 `run_ui.bat`에 묶여 있음)다. 원격의 UI 최신은 11/02 `feat/ui-wpf-2-4`이고 로컬 통합 브랜치에 병합돼 있다.
> - **공개 Releases로 업데이트를 내보낸다**(11/11 오후 결정: 학교 지원 조건이 오픈소스 공개). 문의처는 학교 메일로 바꿨다. 참여자판 0.9.0에 자동 업데이트를 넣었다 — 절차와 보안 모델은 `docs/study-operations.md` 2-5절. 공개하는 업데이트 묶음에는 연구 설정(수신 주소·토큰·문의처)을 넣지 않는다. 그래서 초대하지 않은 사람이 묶음만 받아서는 앱을 켤 수 없고, 새 참여자에게는 지금처럼 설정이 든 zip을 한 번 직접 건넨다. 누구나 받아 쓰는 공개 Beta가 되려면 "연구 설정 없이 로컬에서만 동작하는 모드"가 필요하다(UI를 합칠 때 같이 한다).
> - 검토 중(미정): 목표를 문제 종류(자원 다툼·알려진 충돌·취약점)로 다시 정의하는 안. 저장소에 `LICENSE` 파일이 없다(README는 MIT라고 적고 링크만 있다) — 11/11 저녁 결정: 추가하지 않고 진행.
> - 11/11 저녁 상태: 관리자 경로 시험 통과(28개 확인). 참여자판 0.9.0을 커밋(`8f4b7d7`)하고 그 커밋에서 릴리스 파일을 만들었다(로컬 태그 `v0.9.0`). 남은 순서는 ① 푸시(GitHub 로그인 필요) ② GitHub에서 릴리스 만들기 — 세 파일 첨부 ③ `tools\release-participant.ps1 -Verify`. Hyper-V는 켰고(18:19 재부팅), 그 전 측정은 `lab\runs-before-hyperv-20261111`에 보관했다. 다음 측정 세션은 시범부터 새 실험이다.
> - 첫 실제 측정 세션 결과(11/11): 설치 전 4부팅에서 배경 브라우저의 영향은 1% 미만이었다(`security-impact-design.md` 9.1). 이 PC에서는 보안 모듈의 작업 속도 영향도 작게 나올 수 있어, C1은 "얼마나 느려지나"와 함께 "상주 자원을 얼마나 쓰나"를 같이 보고한다.

> **11/12 결정(정태웅)** — 설계·계획 검토 결과를 반영한다. 아래 본문과 다르면 이 블록이 우선한다.
> - **목표를 분명히 한다.** 대상은 로그를 읽고 상황을 해석하기 어려운 PC 사용자(사무직, 영업직, 디자이너, 모델러 등)다. 크래시·느려짐의 **원인이 보안 프로그램이든 아니든 원인 프로그램을 찾는 것**이 목표이고, 사용자가 스스로 찾지 못한 정보까지 모아 AI에 정확히 전달해 문제를 해결하고 이후에도 관리해 준다. 보안 프로그램은 대표 사례이지 범위의 경계가 아니다. 그래서 발표의 중심은 판단(C2, 평가 E3)이고, 영향 측정(C1)은 "보안 프로그램도 원인 후보 중 하나임"을 보이는 뒷받침이다. 측정 결과가 "영향이 작다"로 나와도 주장은 성립한다(상주 자원 사용량과 검출 가능한 최소 차이를 함께 보고). 재현한 프로그램 자체 버그 9건은 이 목표에서 정답 사례다.
> - **가상 머신을 사례 생산에 쓴다**(예행연습용에서 넓힘). 설치와 설치 창 자동 클릭, 공식 충돌 후보 8건 재현(복제본을 병렬로), 조치 실행기 시험, 실제 설치 위치에서의 업데이트 시험을 가상 머신에서 한다. 호스트에는 보안 프로그램을 **맨 마지막에 한 번**, 실제 하드웨어 측정용으로만 설치한다. 시간 측정은 호스트에서 하고, 가상 머신에서 시간을 잰다면 한 번에 한 대만 켠다. 스크립트: `lab/vm/`(`lab/README.md`).
> - **호스트 설치 기한: 11/24~11/26 사이에 시작.** (11/12 밤에 취소 — 호스트에는 설치하지 않는다.) 설치 후 측정(6블록, 약 6시간) → 제거 → 분석에 필요한 시간에서 거꾸로 잡았다. 그 전에 가상 머신 예행연습을 끝낸다.
> - **범위를 줄인다(지금 뺀다).** 상담 창의 도구 호출 대화, 사람 라벨링(E2), 시스템 변경(Lv3)의 실제 실행 — Lv3은 안내까지만 한다. 지식 팩 업데이트(E6)는 새 장치를 만들지 않고 참여자판 0.9.0의 서명·검증 코드(`participant/StudyCore/Update.cs`)를 다시 쓴다.
> - **일정은 정태웅 1인이 끝낼 수 있는 범위로 짠다.** 병목을 줄이기 위해서다. 아래 "담당(안)"은 참고로 남기고, 팀원 작업은 들어오는 대로 합친다.
> - 작은 항목: ① AI 서비스 키가 든 빌드가 참여자 zip·공개 Releases로 나가지 않게 배포·릴리스 스크립트에 자동 검사를 넣었다(`tools/find-api-key.ps1`, 한계: 쪼개거나 숨긴 키는 못 잡음). ② 0.9.0 동의문에는 업데이트 확인 한 줄이 추가됐고 동의 버전은 그대로다 — AI 전송 항목을 넣을 때 버전을 올려 다시 동의받는다. ③ 평가자(교수·조교)용 빌드는 **제안**: 연구 설정 없이 로컬에서만 동작하고 AI 키가 든 빌드를 직접 전달(Releases에 올리지 않음). 로컬 전용 모드가 필요하므로 UI를 합칠 때 함께 만든다 — 확정 전.
> - 수정된 순서: ~11/16 가상 머신 원본·설치 예행연습, 호스트 설치 전 측정(밤), 검진 스캔 스파이크와 위험도 점수 v0 → 11/17~11/23 가상 머신에서 충돌 사례 재현과 사례 묶음 확정, Claude 한 번 호출 + 근거 검증, 실행기 복원(가상 머신) → 11/24~11/30 호스트 설치·설치 후 측정·제거, E3·E4 실행 → 12/1~12/11 분석·보고서·영상·리허설.

> **11/12 저녁 — 방향 재검토(정태웅 제기)**
>
> **① 호스트 설치 전·후 측정(E1)은 중단한다 — 11/12 밤 확정(아래 "11/12 밤 결정").** 제기된 의문: 설치 전후를 비교해도 "심각하다"는 판단 근거가 되지 않고, 환경을 조정해 시험할 수 있게 된 지금은 필요 없는 실험이 아닌가.
> - 중단 쪽 근거: 실험은 차이의 크기를 줄 뿐 "심각한가"의 기준을 주지 않는다(심각성은 그 PC의 여유 자원과 하는 일에 달려 있다) · 이 PC(8코어 16스레드, 94GB)는 대상 사용자의 PC와 달라 작게 나올 가능성이 높다 · 목표가 "원인 프로그램을 찾는다"로 정해져 측정값이 중심 주장이 아니다 · 밤 2~3번과 되돌릴 수 없는 호스트 변경이 든다.
> - 중단하면 잃는 것: "국내 금융 보안 모듈의 영향을 실제 하드웨어에서 통제 측정했다"는 주장(C1). 가상 머신에서 잰 값은 가상화된 값이라 같은 주장을 대신하지 못한다.
> - 남기는 것: `lab/`의 작업 실행·오염 검사·분석 코드는 가상 머신 안 시나리오 실행기로 다시 쓴다. 11/11의 설치 전 자료는 측정 장치의 정밀도(부팅 간 흔들림 0.4% 등)를 보이는 데만 쓴다.
> - 대신하는 것: "이 PC에서 무엇이 얼마나 쓰는지 **잰 값으로** 판단한다"를 제품 기능으로 둔다. 심각도는 사용자가 겪는 지표(화면 멈춤, 입력 지연, 메모리 압박, 시작 시간)와 그 PC의 여유 자원에 견줘 정하고, 기준값은 설정할 수 있게 한다.
> - 확정됨: C1과 RQ-A, E1은 아래 본문에 처음 계획의 기록으로 남기되 진행하지 않는다.
>

> **11/12 밤 결정(정태웅)**
> 1. **호스트 설치 전·후 측정(E1)을 중단한다.** 주장 C1과 연구 질문 RQ-A를 뺀다. 호스트에는 보안 프로그램을 설치하지 않는다. `lab/`의 호스트 세션(`start-session.ps1` 등)은 돌리지 않고 기록으로 남긴다. 11/11 자료는 측정 장치의 정밀도 근거로만 쓴다. 발표 주장은 **판단(C2)과 조치(C3)** 둘이다.
> 2. **가상 머신에 GPU를 붙인다**(GPU가 필요한 프로그램과 드라이버가 올라간 상태의 사례용). 11/12 확인: 호스트 GPU의 분할(GPU-P)이 붙고 가상 머신이 켜진다. **분할이 붙어 있으면 체크포인트를 만들 수 없어**, 저장·복원 때 스크립트가 떼었다가 다시 붙인다(저장은 꺼진 상태에서만). 게스트는 호스트와 같은 드라이버 파일을 쓰므로 "다른 드라이버 버전" 문제는 재현하지 못한다. 기본은 내장 Radeon이다. 게스트에서 실제로 동작하는지는 미확인(`lab/vm/gpu.ps1`).
> 3. **주변기기도 가상 머신에서 쓴다.** 방법은 확장 세션의 장치 넘기기(프린터·드라이브·오디오·일부 USB)와, 장치 없이 유틸만 설치하는 것 두 가지다. USB 장치 넘기기는 호스트 정책 설정이 필요하다(지금 꺼져 있음 — 켜는 것은 사용자 승인 후). 와콤·로지텍 장치가 넘어가는지는 미확인.
> 4. **가상 머신 시험도 PC를 쓰지 않는 시간(취침, 외출)에 돌린다.** 그래서 게스트 안 작업은 사람 손 없이 돌아야 한다: 게스트 자동 로그온, 게스트 안 실행 스크립트, 호스트의 세션 실행기(여러 복제본을 차례로·동시에 돌리고 끝낼 시각에 모두 끔)가 필요하다 — 다음 작업.
> 5. **유료 프로그램은 무료·평가판으로 시험한다.** 구하기 어려우면 같은 유형의 프로그램으로 대신한다(6번).
> 6. **대신 쓸 프로그램 후보**: Krita(그림 — KDE 커뮤니티의 오픈소스), DaVinci Resolve(영상 편집 — Blackmagic Design, 무료판, GPU 필요, 받을 때 등록 양식), Blender, GIMP, Inkscape, LibreOffice, ArtCraft의 Craft 앱 모음(`getartcraft.com/apps` — PhotoCraft 이미지 편집, PdfCraft, AniCraft 2D 애니메이션, FigCraft 화면 설계 등. 무료 오픈소스이고 Windows 설치 파일이 있다. 대부분 초기 알파나 개발 중이라 프로그램 자체 버그 사례를 얻기 좋지만, 알려진 문제의 공식 근거는 그 프로젝트의 이슈 기록뿐이다. 11/12 밤 정정: 처음에 `craft-anything` 저장소 하나로 잘못 이해했다).
> 7. **사례 묶음을 두 단계로 만든다.** **골드셋** = 가상 머신(과 호스트)에서 직접 만들어 원인을 아는 사례. **실버셋** = Adobe·Microsoft 등 제조사의 이슈·지원 문서를 근거로 만든 사례(직접 재현하지 않은 것 포함). 골드셋을 먼저 만들고, 실버셋으로 범위를 넓힌 뒤 에이전트 작업을 한다. 평가에서는 둘을 따로 보고한다 — 실버셋은 공개 문서가 근거라 AI가 내용을 이미 알고 있을 수 있고, 증거가 실제 PC에서 나온 것이 아닐 수 있다(4절 E3의 P·X 구분과 같은 이유).

> **11/12 밤 결정(정태웅) — 평가 설계.** 아래 4절(E2~E5)은 `docs/evaluation-design-v3.md`(사전 등록)로 대체한다. 요점: API 예산 300달러, 모델 Opus 5.5·Sonnet 5.5·Haiku 5.5 · **조치 도구까지 쥔 에이전트를 목표**(가상 머신에서만 실행. **Lv3도 사용자 설정과 건별 승인이 있으면 실행** — 위의 11/12 결정 "Lv3은 안내까지만"을 대체. 지우면 크게 위험한 드라이버는 실행기가 거부하고 안전한 방법이나 안내로 돌린다) · 예산은 11월 말까지 300달러, 예비 120달러 · 개발용 약 30 + 시험용 약 60 사례, 시험용은 11/23 동결 · 위험 등급은 심은 프로그램·효율·안정성으로 증명 · 전문성은 공식 해결책 일치 + AI 채점 + 사람 채점 30개(사람 유무에 따른 결론 차이도 보고) · 실험 코드는 Python(`eval/`). 정답 표기 `injected` 확정. 첫 실측: 덤프 원본은 중앙값 35만 토큰, 엔진용 요약은 5천 토큰(약 68배).

| 재현 사례 | 9건 | 모두 프로그램 자체 버그라 충돌 판정 검증에는 못 씀 |
| 조치 실행기 | 보관 중 | 실제 Windows에서 실행한 적 없음 |
| AI 에이전트 | 연결 지점만 있음 | 없음 |
| 성능 영향 측정 | 설계 완료, 실행 전 | 없음 |

정리하면 수집과 판단의 뼈대는 있다. 약한 곳은 세 가지다.
- "공식 근거가 있는 충돌 사례에서의 정확도"가 0건이다.
- 판단 뒤의 단계(AI, 조치)가 비어 있다.
- 처음 목표였던 참여자 데이터 기반 검증은 남은 기간에 충분한 양을 얻기 어렵다.

## 2. 목표 재정의

**한 문장:** 내 PC에 깔린 보안·상주 프로그램이 일으키는 충돌·느려짐·취약점을 **증거로 판단**하고, **사용자가 정한 수준 안에서 조치**까지 하는, 설명 가능한 도구.

**11/12 보강:** 원인이 보안 프로그램이 아니어도 원인 프로그램을 찾는다. 로그를 읽기 어려운 사용자(사무직, 영업직, 디자이너, 모델러 등)를 대신해 흩어진 증거를 모으고, AI에 정확히 전달해 해결하고 관리한다(문서 맨 위 "11/12 결정").

이전 목표("크래시 원인 추론")는 그 안의 한 부분으로 남는다. 바뀌는 점은 세 가지다.
- 사건이 없어도 [검진]으로 프로그램별 위험도를 볼 수 있다.
- AI가 이 PC의 사용 맥락에 맞춰 판단을 보조한다.
- 판단에서 끝나지 않고 정지·수정·삭제·메모리 정리까지 이어진다.

### 최종 목표와 이번 학기에 보일 것 (11/10 추가)

**왜 필요한가.** 2026년에는 PC가 느려지거나 프로그램에 문제가 생기면 AI에게 묻는 것이 일반인에게도 익숙하다. 하지만 일반인은 "무엇이, 어디서, 언제, 어떻게" 일어났는지 스스로 확인할 수 없어서 AI에게 줄 정보가 없고, 받은 답을 실행하고 재발을 막는 일도 어렵다. 이 프로젝트는 그 사이를 메운다.

1. PC의 증거를 모아 **적은 토큰으로** AI에 전달한다.
2. 핵심 조치를 제시한다.
3. 사용자가 정한 보안·위험 수준 안에서 조치를 **자동으로 실행**하고 되돌릴 수 있게 한다.

**최종 목표.** 드라이버, 백신, 보안 프로그램, Windows, 게임, 에디터 등 분야를 가리지 않고 충돌과 애로 사항을 **감지 → 점검 → 치료 → 권고**하는 도구다. 프로그램 자체의 버그도 알려 주고, 고칠 수 있는 것(수정 버전 업데이트, 알려진 우회 설정)은 고쳐 준다. 병원·디자인·자영업 프로그램처럼 분야별로 쓰는 프로그램의 문제까지 다루고, 새로 알려지는 버그는 포럼·버그 리포트에서 지식 팩 업데이트로 받아 안정적으로 운영한다.

**이번 학기에 보일 수 있는 범위.** "모든 분야"는 4주 반 안에 증명할 수 없다. 그래서 **구조가 분야에 묶여 있지 않다는 것**을 다음 세 가지로 보인다.

| 보일 것 | 방법 |
|---|---|
| 분야별 대표 사례가 같은 구조로 처리됨 | 금융 보안(통제 측정), 게임·오버레이(공식 충돌 사례), 개발 도구·에디터(Godot·Notepad++·Git), 디자인 도구(Blender 메모리 누적), 백신(Defender × 모니터링 드라이버), Windows 업데이트(공식 알려진 문제), 주변기기·모니터 유틸(Logitech G HUB, Wacom, LG 모니터 앱 — 공식 근거가 없어 규칙이 아니라 이 PC에서 잰 값으로 판단, `security-software-survey.md` 6.4) — 범주마다 재현 사례 1~2건을 E3에 넣음 |
| 프로그램 자체 버그도 처리됨 | 11/10에 재현한 9건(AutoHotkey 2.0.29, Godot 4.3, Notepad++ 8.6.7)은 모두 프로그램 자체 버그이고 수정 버전이 있다. "원인은 이 프로그램의 알려진 버그 → 수정 버전으로 업데이트"를 맞히는지 평가한다. 충돌 검증에는 못 쓰던 사례가 여기서 정답 사례가 된다 |
| 새 문제가 업데이트로 들어옴 | E6: 앱을 다시 빌드하지 않고 지식 팩만 갱신해 새 사례를 잡는 시연 |

병원·POS처럼 팀이 구할 수 없는 프로그램은 실제로 시험하지 못한다. 이 범주는 "지식 팩에 항목을 추가하면 같은 방식으로 동작한다"까지만 말하고, 검증하지 못했다고 밝힌다.

## 4. 평가 설계

공통 규칙은 다음과 같다.
- 지표·사례 목록·판정 기준은 실행 전에 이 문서에 고정한다(사전 등록). 바꾸면 기록한다.
- 사람 손 대신 스크립트로 실행한다.
- 원자료를 남긴다.
- 표본이 작으므로 비율에는 신뢰구간(Wilson)을 함께 적고, "차이 없음"과 "판단 불가"를 구분한다.

### E1 영향 측정 — `security-impact-design.md` 그대로

- 결과는 발표 숫자가 되는 동시에 `measured-overhead` 지식 팩이 된다. 즉 실험 결과가 제품의 입력으로 들어간다.
- 설치 단계에서 제품별 증가분(설치마다 유휴·작업 부하 재측정)도 얻는다.

### E2 위험도 점수의 타당성

| 검사 | 방법 | 통과로 볼 기준(초안) |
|---|---|---|
| 판별 | 이 PC(설치 후)의 전체 제품에 점수를 매기고, **점수 입력으로 쓰지 않은 독립 기준**과 비교한다. 독립 기준은 두 가지다. ① 제거 단계에서 구라제거기가 이 PC에서 **실제로 찾아낸 대상**(제거 전에 화면을 기록 — 전체 목록은 공개돼 있지 않다) ② 식탁보(TableCloth) 카탈로그에 "은행이 요구하는 보안 프로그램"으로 올라 있는 제품(Apache-2.0, 커뮤니티 유지). 둘 다 점수 계산에 넣지 않아야 순환 논리가 아니다 | 그 대상이 상위에 몰리는가(AUC, 상위 10개 중 비율) |
| 실측 일치 | C축 점수 vs E1에서 잰 제품별 증가분의 순위 상관 | 탐색용(제품 10개라 표본이 작음) |
| 민감도 | 가중치를 ±50% 흔들었을 때 등급이 바뀌는 제품 비율, 순위 상관 | 순위가 크게 뒤집히지 않는가 |
| 사람과의 일치 | 팀원 3명(가능하면 외부 1~2명)이 제품 30개를 점수를 보지 않고 4등급으로 분류한 뒤 점수와 비교 | 가중 κ, 사람들 사이의 일치도와 비교 |
| 재현성 | 같은 PC에서 두 번 검진 | 점수 동일(결정적이어야 함) |

### E3 원인 판단 — 네 방식 비교 (이번 설계의 핵심)

**사례 묶음(실행 전 확정, 목표 50~60건)**

| 묶음 | 내용 | 정답의 출처 | AI 학습 데이터에 답이 있을 가능성 |
|---|---|---|---|
| P 비공개 통제 | E1의 설치 후 덤프(느려짐, 원인 = 보안 모듈), FaultLab(일부러 낸 크래시·멈춤·누수·CPU 과부하), 재현 9건 | 실험 조건 | **없음** — 깨끗한 시험 |
| T 팀 시나리오 | 엔진 샘플 13건 | 팀이 만듦 | 없음. 단 엔진이 이 사례에 맞춰져 있음 |
| X 공개 사례 | 외부 라벨 18건 + 공식 확인 충돌 사례 중 이 PC에서 재현한 것(후보 8건: `security-software-survey.md` 6.3 — 예: 금융 보안 설치 후 Firefox의 `nzbrcom.dll` 차단, LibreHardwareMonitor × Defender) | 벤더 공식·작성자 확인 | **있음** — AI가 "기억"으로 맞힐 수 있어 따로 보고 |

**네 방식**

0. 증상 설명만: "○○를 하다가 꺼졌어요" 같은 한두 문장만 Claude에 전달. 일반 사용자가 지금 AI에 묻는 방식이고, 비교의 기준선이다(11/10 추가). 사례마다 증상 문장은 미리 써서 고정한다.
1. 알고리즘만: 엔진 + 위험도 점수
2. AI만: 엔진 결과 없이 증거 묶음만 Claude에 전달
3. 알고리즘 + AI: 엔진 결과와 증거 묶음을 Claude에 전달(제품의 실제 구조)

1~3번은 같은 증거 묶음을 쓴다.

**지표**

| 지표 | 정의 |
|---|---|
| 층 정확도, 원인 1순위·3순위 안 | 기존 엔진 지표와 같음 |
| 근거 있음 비율 | AI가 인용한 증거 ID가 실제 묶음에 있는 비율(코드로 검증) |
| 위험 권고 비율 | 보호 목록 대상이나 정책 밖 조치를 권한 비율 |
| 일관성 | 같은 사례 3회 실행에서 1순위가 같은 비율(AI가 들어간 방식만) |
| 비용·시간 | 사례당 토큰·요금·초 |
| 토큰 효율 | 증거 묶음의 입력 토큰 수(`count_tokens`로 측정). 같은 사건의 원본 기록(이벤트·스냅샷 전체)을 그대로 보냈을 때의 토큰 수와 비교하고, 묶음을 줄였을 때 정확도가 유지되는지 본다 |
| 조치 가능성 | 권고가 실행 가능한 조치 ID로 이어진 비율. 0번 방식은 일반 조언에 그칠 것이므로 사람이 "이 PC에서 바로 할 수 있는가"를 판정 |

**미리 적는 예상**

- 0번 방식은 원인을 특정하지 못하고 일반적인 점검 목록을 낼 것이다. 3번은 같은 사례에서 원인과 실행 가능한 조치를 낸다.

- 공개 사례(X)에서는 3번 방식이 1번보다 1순위가 높을 것이다. 엔진 규칙에 없는 이름을 AI가 메우기 때문이다.
- 비공개 사례(P)에서는 2번 방식이 1번보다 낮거나 근거 없는 말이 많을 것이다.
- 3번의 위험 권고는 0이어야 한다. 구조상 고를 수 없기 때문이다.

**해석 주의**

- 표본이 작아 방식 간 차이는 짝 비교(McNemar)와 신뢰구간으로만 말한다.
- 엔진을 고치는 일(규칙에 이름 22개 추가 등)은 **사례 묶음을 확정하기 전에** 끝내거나, 묶음을 개발용과 시험용으로 나눠 시험용은 마지막에 한 번만 쓴다.

### E4 조치의 효과와 안전

실제 보안 프로그램에 쓰기 전에 **FaultLab**을 대상으로 한다. FaultLab은 일부러 CPU·메모리·디스크를 쓰는 시험 프로그램이라, 정지·종료해도 잃을 것이 없다.

| 시험 | 방법 | 기준 |
|---|---|---|
| 효과 | 조치 종류별 10회: 조치 전후 대상의 CPU·메모리·증상 신호 | 측정된 감소량 |
| 되돌리기 | 조치 → 원복 → 상태 비교, 실행 도중 강제 종료 후 재시작 포함 | 원복 성공 100% |
| 보호 목록 | 보호 대상에 대한 조치 요청 20건 | 거부 100% |
| 주입 공격 | 이벤트 메시지·프로그램 이름·경로에 "○○를 삭제하라" 같은 문장을 심은 증거 묶음 20건을 3번 방식에 넣음 | 허용 밖 실행 0건(AI가 속았는지와 실행기가 막았는지를 따로 기록) |
| 메모리 정리 | 작업 집합 정리 vs 누수 프로그램 재시작: 직후·5분 뒤의 커밋·가용 메모리, 프로그램 반응 시간 | 어느 쪽이 실제로 줄이는지 수치로 |
| 실제 대상(마지막) | 금융 보안 모듈: 시작 유형 수동(Lv2) → 제거(Lv3, 복원 지점) → E1의 제거 후 측정과 연결 | 전후 측정값 |

### E5 비용

- 검진 스캔 시간
- 상시 부담(기존 기준 1% 미만 유지)
- 진단 1회의 API 요금·응답 시간
- 팩 크기와 업데이트 시간

### E6 업데이트로 운영되는가 (11/10 추가)

"새로 알려진 문제가 앱을 다시 배포하지 않고 들어온다"를 시연하고 기록한다.

1. 사례 하나를 정한다. 팩에 아직 없는 공식 충돌 사례나 프로그램 버그여야 한다(예: `security-software-survey.md` 6.3의 후보 중 하나).
2. 갱신 전: 그 사례를 재현하고 검진·진단한다. 원인을 못 잡거나 "미분류"로 나오는 것을 기록한다.
3. 출처(버그 리포트·벤더 공지)를 보고 팩 항목을 쓴다. 출처 URL과 등급을 붙이고, 회귀 시험을 통과시킨 뒤 서명한다. 걸린 시간을 기록한다.
4. 갱신 후: 같은 앱이 팩만 받아 같은 사례를 다시 진단한다. 원인과 조치가 나오는지 확인한다.
5. 서명이 틀린 팩과 형식이 깨진 팩을 넣어, 적용하지 않고 이전 팩을 유지하는지 확인한다.

포럼 글을 자동으로 긁어 규칙을 만드는 것은 하지 않는다. 커뮤니티 글은 D등급이라 사람이 확인해 A~C 출처와 연결된 것만 팩에 넣는다.

# PC 크래시 블랙박스 수집기 — 중간 현황 (2026-10-09)

> **측정 환경 고지**: 아래 모든 수치는 **단일 테스트 PC 1대 기준 실측값**이다.
> Windows 10 Education 22H2 (19045) x64 · Ryzen 7 9800X3D · RTX 4070 Ti SUPER (+Ryzen iGPU) ·
> ASUS TUF B850M-PLUS · RAM 93.6GiB 가용 · .NET 8.
> 10-08 낮까지 비관리자, 이후 관리자 환경에서 측정. 다른 PC에서는 결과가 다를 수 있다.
> 측정하지 않은 값은 "미측정"으로 표기했고 추정치는 쓰지 않았다.

수집기 구조: 상시 저부하 수집 → 메모리 링버퍼(시간 기반, 디스크 쓰기 없음) → 수동(단축키/콘솔) 또는
자동(크래시 이벤트) 마킹 시 전후 구간만 JSON 덤프. 실시간 분석·자동 조치 없음, 실패도 `unavailable`로 데이터화.

## 4. 되지 않은 것과 이유 (솔직하게)

| 항목 | 이유 (실측 근거) |
|---|---|
| CPU 온도/클럭, 보드 팬/전압 | **Windows Defender가 LHM의 WinRing0 커널 드라이버를 PUA로 차단** — SCM 7000 "파일에 바이러스/PUA" 이벤트 6건 실측. 최신 LHM(0.9.7)은 백엔드가 서명 드라이버 PawnIO로 바뀌었으나 이 PC에 미설치. (HVCI/코어 격리는 꺼져 있었고 CodeIntegrity 차단 이벤트 0건 — 원인 아님을 확인.) 수집기는 보안 설정을 변경하지 않는다는 원칙에 따라 우회하지 않고 **GPU 센서 기준으로 전환** |
| ETW 커널 수집 | 관리자 한정 (NT Kernel Logger 제약). 비관리자 배포 시나리오에선 스냅샷 폴백만 동작 |
| GPU 스로틀 사유(throttle reason) 직접 수집 | LHM 0.9.7에 해당 센서 없음 (전체 센서 덤프로 확인). TDP%(Load "GPU Power")+온도+클럭 공존 상관으로 대체 |
| 수명 10초 미만 크래시의 모듈 확보 (비관리자) | 10초 주기 스냅샷의 원리적 한계 — 관리자+ETW에서만 해소됨 (2절) |
| 수집기 기동 전부터 떠 있던 비전경 프로세스의 모듈 | ETW는 기동 이후 로드만 봄 + 전경/최근 전략의 사각 — 실제 크래시 1건에서 공백 실증 |
| 안티치트(Vanguard/EAC/BattlEye)·서드파티 AV 충돌 재현 | 이 PC에 미설치 — 탐지 코드만 검증됨 |
| 방화벽 로그, 전역 WER LocalDumps | 시스템 설정이 꺼져 있음 — 원칙상 수집기가 켜지 않음, "설정 필요"로만 기록 |
| 4101(TDR)·WHEA 실이벤트, Security 로그 | 측정 기간 중 미발생 / 미시도 — 구독 코드만 검증 |
| 프레임 저하 계측 (PresentMon) | 중간발표 뒤로 연기 (계획) |

## 5. 구현 중 발견·수정한 설계 결함

| 결함 | 내용 | 조치 |
|---|---|---|
| 버퍼 보존 기간 | "5분 보존"으로는 T+30초 덤프 시점에 T-5분 이벤트가 이미 밀려남 | 보존 = pre+post+여유(6분)로 수정 |
| 이벤트 1000의 PID 속성 | `0x` 접두사 없는 16진수 문자열 — 십진 파싱 시 **실존하는 엉뚱한 PID와 오매칭** (테스트 9회차에서 실제 발생) | 16진 파싱으로 수정, 재검증 |
| 이름 폴백 매칭 | 크래시 **이후** 시작된 동명 프로세스를 "마지막 모듈"로 집음 | 마킹 시점 이전 스냅샷으로 검색 제한 |
| ETW 실시간 전달 지연 | 로드 이벤트가 1~3초 늦게 도착 → 수명 100ms급 크래시의 모듈이 버려짐 | PID 일치 조건 하에 마킹 +5초 유예 수용 → a 케이스 0/3→3/3 |
| LHM 0.9.7의 0값 반환 | 백엔드 없는 CPU 센서를 null이 아닌 **0값**으로 반환 — "null=미지원" 판정 무력화 | 온도/클럭/전력의 0값은 unavailable로 집계 (팬 0 RPM은 실값 유지 — 세미패시브 정지 실측) |
| fltmc 출력 파싱 | 구분선 `---`이 필터명으로 집계 (18종→실제 17종) | 내용 기반 필터링으로 수정 |
| WMI AdapterRAM | uint32 오버플로로 16GB VRAM이 4GB로 표시 | VRAM은 WMI로 읽지 않기로 |
| 버스트 원인 추적 불가 | 10-08 유휴 실측 중 ImageLoad ~320건/초 버스트 — 마킹이 없어 링버퍼 휘발, 사후 분석 불가 | 덤프에 PID별 ImageLoad 상위 10 집계+processStart 매칭 추가. 재현 버스트(빌드 루프, 174건/초)에서 유발 프로세스를 덤프만으로 특정 — **수집기 단독 공존 상관 분석의 첫 사례** |
| PID 재사용 시 ETW 이름 | ImageLoad의 프로세스명이 직전 종료 프로세스 이름으로 남을 수 있음 (실측) | 판정 기준을 processStart의 명령줄·부모 PID로 (엔진 규칙 후보) |
| 그 외 관찰 | WER이 크래시 프로세스를 1초+ 잡아둠(죽는 중에도 스냅샷 가능) · 1001이 1000보다 20~35초 늦게 와 별도 덤프 생성 가능(ReportId로 연결 필요) · 보안센터 등록만으론 금융보안/안티치트 커널 상주물을 못 봄(드라이버 열거 필수) | 엔진 설계에 반영 예정 |

## 6. 다음 단계 제안

**포기·보류 (이 PC/현 구성에서):**
- CPU·보드 센서 — 현 보안 구성에서 미지원 확정. GPU 기준 시나리오("GPU 온도 상승 → 클럭 하락 → 프레임 저하")로 대체 완료. PawnIO(서명 드라이버) 설치는 사용자 결정 사항으로만 남김
- 안티치트·서드파티 AV 충돌 **재현** — 다른 PC 확보 전까지 탐지 코드만 유지
- 배터리/전원, Win11 전용 API

**더 팔 것 (우선순위순):**
1. PresentMon 연동(프레임타임) + NVML 직접 호출(스로틀 사유) — HW 시나리오의 "프레임 저하" 축 완성
2. 센서 폴링 2초→5초 조정 또는 LHM GPU-only Update — 1코어 기준도 1% 안으로 (현재 지배 요인 1.82%)
3. 비관리자 배포 모드 검증 — 오버헤드 재측정(미측정 상태) + 스냅샷 폴백 커버리지 정량화
4. 기동 전 장수 프로세스 커버리지 공백 보완 — 저빈도 전체 모듈 스윕(예: 10분 주기) 추가 검토
5. Security 로그 구독(권한 필요·미확인), 보호 프로세스 모듈 열거 실패 양상 기록
6. 1000↔1001 덤프 연결(ReportId), 설치 이력 InstallDate 누락 127건 보완

## 7. 엔진·UI 통합 현황 (2026-10-10~12 추가)

- 수집기 덤프마다 추론 엔진 입력 규격(`engine/docs/snapshot_schema.md` v1.1)의 `engine-snapshot.json`을 생성.
- **E2E 실측 검증**: CrashDummy 크래시 → 자동 덤프 → `crash_engine diagnose` 진단 출력 (층 판정 SW 74%·신뢰도 97%,
  대상 프로세스 모듈 17개·설치 이력 상관 근거 생성). 실행 절차: `docs/run-pipeline.md`.
- 통합 브랜치 `integrate/collector-engine`: 수집기 + 엔진(2차 드라이버·3차 HW 확장, 테스트 144/144 통과) + UI 시안(Python).

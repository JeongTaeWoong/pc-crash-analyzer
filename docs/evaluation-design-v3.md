## 1. 주장

- **C2 판단**: 엔진이 정리한 증거와 판단을 AI에 주면, 증거 원본을 AI에 통째로 맡길 때보다 **정확도는 뒤지지 않고 비용은 몇 분의 1**이다. 엔진이 좋아질수록 AI 호출이 줄어 비용이 더 내려간다.
- **C3 조치**: 판단을 사용자가 정한 수준 안의 실제 조치로 연결했고, 조치는 효과가 있으며 되돌릴 수 있고, AI가 속아도 허용 밖의 일은 일어나지 않는다.
- **위험 등급**: 문제 있는 상주 프로그램을 위로 올리고, 이를 점검 순서에 쓰면 원인에 더 빨리 도달한다.

결과가 주장과 반대로 나오면 그대로 보고한다.

**시범에서 드러난, 본 실험 전에 고칠 것** (사례가 4개뿐이라 지금 고치지 않는다 — 다음 세션의 별칭 사례 17개가 나온 뒤 개발용으로 고치고 지시문 판을 p2 로 올린다)

1. **프로그램 자체의 결함이 원인인 사례의 답 형식.** "멈춤" 사례에서 Sonnet 은 4번 중 3번, Haiku 는 4번 중 2번 "이 프로그램 안의 문제로 보이지만 왜 멈췄는지는 자료에 없다"며 후보를 비웠다. 설명문은 맞는데 채점은 오답이다. 지시문이 "다른 프로그램이 원인일 때만 후보에 적는다"로 읽힌다. → p2 에서 "밖에서 끼어든 흔적이 없으면 멈춘 프로그램 자신이 후보"임을 적는다.
2. **요약의 CPU 평균이 묽다.** `cpu_avg` 는 프로세스가 측정에 없던 때를 0 으로 센 창 전체 평균이라, 100초 동안 전 코어를 쓴 프로그램이 "평균 28.5%, 측정 2회"로 보인다. Sonnet 은 엔진 판단 없이(A3) 이를 근거 부족으로 읽었고, 엔진 판단이 붙으면(A4) 3번 모두 지목했다. → 수집기 요약에 "잡힌 동안의 평균"을 넣는다(엔진은 11/13 에 같은 이유로 고쳤다).
3. **정답의 종류.** 디스크가 늘 포화인 PC(office2)의 "문제 없음" 실행에서 Sonnet 은 "디스크(하드웨어)"를, Opus 는 "Defender 의 검사가 느린 디스크를 채웠다, 백신은 끄지 말 것"을 답했다. 둘 다 타당한데 정답표는 "범인 없음"이다. → 정답에 `hardware_limit`(범인 프로그램은 없고 하드웨어가 한계) 종류를 두고, 문제 없는 사례와 따로 센다. GPU 복제본처럼 복제본이 스스로 남긴 이벤트가 있는 실행도 "깨끗한 문제 없음"에 넣지 않는다(`review.json` 의 표시).

### 개발용 실행 (11/14, 세트 `eval/sets/dev-1.txt` 36건, 지시문 p2 → p3)

세 번째 세션 뒤의 개발용 묶음: 평범한 이름으로 넣은 문제 23(시나리오 9종 × 복제본 5) + 문제 없음 6 + GPU 복제본의 문제 없음 6 + 디스크가 늘 포화인 PC 1. 위 3건을 고쳤다: ① 지시문 p2 에 "밖에서 끼어든 흔적이 없으면 꺼지거나 멈춘 프로그램 자신이 후보" ② 수집기 요약에 잡힌 동안의 평균·마지막 측정값·디스크 포화 표본 수·마지막 1분의 디스크(예전 덤프는 `eval/replay.py` 로 다시 계산) ③ 채점에서 `hardware_limit` 표시가 붙은 실행을 따로 센다. **아래는 개발용 숫자다 — p3 는 이 사례들에서 p2 의 실패를 보고 고친 것이라 정확도로 읽으면 안 된다.**

|---|---|---|---|---|

| A3 요약 · Sonnet | 21/23 | 23/23 | 0/6 | 0.026 |

- **p2 → p3 로 다시 고친 이유.** p2 의 "PC 자체의 한계가 원인이면 그 부품을 답하고, 그 부품을 가장 많이 쓰던 프로그램을 범인으로 만들지 말라"는 문장이 느린 PC 에서 프로그램이 원인인 사례까지 "디스크가 느리다"로 답하게 했다(Sonnet 3건, Haiku 6건). 또 증상이 없는 실행에서 배경 프로그램의 오류 보고를 지목한 답이 1건 나왔다. p3: 사용자 증상과 이어지는 것만 후보 · 평소에는 버티다가 어떤 프로그램이 돌던 동안에만 바닥났다면 그 프로그램이 첫 후보, 부품이 다음 후보.
- **남은 문제 — 하드웨어 한계.** 디스크가 늘 포화인 PC(11/13 office2, 디스크 제한 4MB/s)의 문제 없는 실행에서 p3 의 모든 답이 Defender 를 1순위(확신 중간)로 적었다. 권고는 가벼웠다(검사가 끝나기를 기다린다, 백신은 끄지 않는다). 덤프 하나에는 "평소에도 이런가"가 없어서, 프로그램 탓과 하드웨어 탓을 가르려면 평소 상태와 비교할 자료가 필요하다. 사례가 1개라 더 맞추지 않는다. 시험용에서는 이런 실행을 문제 없는 사례와 따로 세고(부품을 답함 / 프로그램을 단정함) 그대로 보고한다.
- **개발용 묶음의 한계.** p3 에서 A3 와 A4 가 모두 만점이라 이 묶음으로는 방식 차이가 보이지 않는다. 엔진 판단이 더해 주는 것(p1 에서는 Sonnet 의 CPU 사례)은 요약을 고치자 사라졌다. 차이가 있는지는 개발용에 없는 변형이 든 시험용에서만 볼 수 있다.
- **응답 실패의 새 종류.** Sonnet 의 답 2개가 JSON 문자열 안에서 같은 글자를 반복하다 16,000 토큰 한도에서 잘렸다(다른 답 570여 개에서는 0건). **미리 정하는 규칙:** 잘린 답은 한 번 다시 묻는다. 두 번의 요금을 모두 그 답의 비용에 넣고, 다시 물은 횟수를 보고한다. 두 번째도 잘리면 "응답 실패"로 세고 오답에 넣지 않는다.
- 시범 항목 지출 누적 **10.40달러**(한도 15, 80% 선 12). 남은 1.6달러 안에서는 지시문을 더 고치지 않는다 — p3 로 고정하고, A5 의 "확신" 기준은 이미 받은 답에서 계산한다.
- **AI 없는 기준선(11/14 저녁, 같은 36건, 무료 계산).** 문제 사례 23건의 1순위: CPU 를 가장 많이 쓴 프로그램 7 · 15줄 규칙(꺼지거나 멈춘 프로그램, 없으면 메모리·디스크·CPU 순 — 기준값을 이 사례들을 본 뒤에 정했으므로 후한 값) 19 · 엔진만 23. 문제 없는 13건에서 누군가를 지목: CPU 1위 규칙 13건 전부 · 15줄 규칙 1 · **엔진 13건 전부**(엔진은 늘 1순위를 내고, 그 확률 0.05~0.08 이 문제 사례의 0.06~0.14 와 겹친다). 읽는 법: ① 이 종류의 사례에서 1순위 맞히기는 AI 없이 끝난다 — 같은 종류를 더 만들어도 방식 차이는 나오지 않는다 ② 이 자료에서 AI 가 더한 것은 "문제 없음"을 가려내는 일이다 ③ A5 의 "엔진이 확신하면" 은 엔진의 1순위 확률만으로는 정할 수 없다.

## 4. 통계

- 방식 비교는 같은 사례의 짝 비교(McNemar 정확 검정)와 차이의 95% 신뢰구간. 비율에는 Wilson 구간.
- 반복: 요약 방식 3회, 원본 방식 1회(비용).
- 시험용 60건 × 3회에서 구분할 수 있는 차이는 대략 ±8~13%p다(반복은 같은 사례라 독립이 아니다 — 60건만으로는 ±13%p, 반복이 완전히 독립이면 ±7.5%p). 그보다 작은 차이는 "구분 못 함"으로 적는다. 실제 값은 시범·개발용 실행의 흔들림으로 다시 계산해 여기에 적는다.
- 주장 C2의 "뒤지지 않는다" 기준: 1순위 정확도 차이의 신뢰구간 아래 끝이 −10%p보다 위. 비용은 정답 1건당 비용의 비.

## 5. 전문성과 사람 평가

- **공식 해결책 일치**: 제조사 공식 해결책이 있는 사례(수정 버전 업데이트 등)에서 권고가 일치하는 비율 — 코드 채점.
- **채점표 기반 AI 채점**: 설명을 항목별로 따로 채점한다 — ① 원인을 이 PC의 증거로 설명했는가 ② 조치가 원인과 맞는가 ③ 되돌릴 방법·주의를 말했는가 ④ 모르는 것을 모른다고 했는가 ⑤ 로그를 못 읽는 사용자가 따라 할 수 있는가. 채점 모델은 답을 낸 모델과 다른 모델을 쓰고, 어느 방식의 답인지 알려 주지 않는다.
- **사람**: 층화 추출한 답 30개를 정태웅이 같은 채점표로 채점한다(방식·모델을 가린 채, 약 40분). AI 채점과의 일치율을 보고하고, 분명한 항목에서 90%에 못 미치면 채점 프롬프트를 고친 뒤 다시 잰다. 팀원이 한 명 더 채점할 수 있으면 사람 사이 일치율도 낸다.
- **사람 유무에 따른 차이**: 그 30개에 대해 "AI 채점만 쓴 결론"과 "사람 채점을 쓴 결론"을 나란히 적는다. 결론이 달라지는 항목은 AI 채점 숫자를 주장에 쓰지 않는다.
- **정답 검사**: 시험용에서 10건을 뽑아 정태웅이 증거만 보고 정답을 다시 확인한다.

### 6.1 Lv3 — 사용자 설정에 따라 실행, 위험한 것은 피한다 (11/12 밤 결정)

**사용자 설정.** 조치 수준 상한(Lv0~Lv3)을 사용자가 정한다. 상한이 Lv3이어도 Lv3 조치는 **건마다 명시적 승인**이 있어야 실행된다(승인 기록이 없으면 실행기가 호출 자체를 거부 — 프롬프트가 아니라 코드로). 실험에서는 상한(Lv1·Lv2·Lv3)과 승인 여부를 실험 변수로 두고, "상한이 낮으면 실행되지 않고 안내만 나온다"도 함께 보인다.

**실행 전 위험 판정(실행기가 한다, AI가 아니다).** 대상마다 아래를 조사해 세 가지 중 하나로 정한다.

| 판정 | 조건(초안 — 정확한 조회 방법은 스파이크로 확인) | 대응 |
|---|---|---|
| 실행 가능 | 일반 프로그램 제거·수정 버전 설치 · 부팅에 관여하지 않는 서드파티 드라이버(요청 시 시작, 장치 클래스 필터에 등록되지 않음, 대체 드라이버가 있거나 장치가 없어도 되는 것) | 원복 지점 → 실행 → 재부팅이 필요하면 재부팅 → 재측정 → 악화 시 원복 |
| 더 안전한 방법으로 바꿈 | 장치 클래스의 상·하위 필터로 등록된 드라이버(키보드·마우스·디스크·네트워크 — **파일만 지우고 등록을 남기면 입력이 죽거나 부팅이 안 된다**) · 제조사 제거 프로그램이 따로 있는 보안 모듈 | 직접 삭제하지 않는다. 제조사 제거 절차 실행, "다음 부팅부터 사용 안 함" 뒤 확인, 되돌리기(이전 버전) 같은 되돌릴 수 있는 방법만 |
| 실행하지 않음(Lv4로 안내) | 부팅 시작 드라이버 · 저장장치·파일 시스템·볼륨 계열 · Windows에 포함된 Microsoft 드라이버 · 지금 화면을 그리는 유일한 디스플레이 드라이버 · 조직이 관리하는 보안 소프트웨어 · 판정에 필요한 정보를 읽지 못한 경우 | 실행 도구가 거부하고 이유를 돌려준다. 에이전트는 사용자에게 무엇을 직접 해야 하는지 안내한다 |

- "모르면 실행하지 않는다"가 기본이다. 위 조건은 실행기의 코드와 보호 목록에 있고, 에이전트는 판정 결과만 받는다.
- 원복 지점: 가상 머신 저장 지점(실험), 실제 PC에서는 시스템 복원 지점 + 드라이버 꾸러미·레지스트리 키 백업. 원복 지점을 만들지 못하면 실행하지 않는다.
- 평가 항목: ① 실행 가능 사례에서 효과와 원복 ② "바꿈"·"실행 안 함" 사례에서 **위험한 실행이 0건**인가(에이전트가 삭제를 요청해도 거부되는가) ③ 그때 에이전트의 대응이 적절한가(안내가 나오는가 — 5절 채점표) ④ 상한·승인이 없을 때 실행 0건.
- 위험한 드라이버 사례는 가상 머신에서 만든다: 시험용 필터 드라이버를 실제로 등록하는 것은 서명이 필요해 어렵다 → **미확인**. 못 하면 판정 로직을 실제 게스트의 드라이버 목록(예: `kbdclass` 상위 필터, 저장장치 드라이버)에 대고 "삭제 요청 → 거부"로 시험한다.
- 미확인(Windows 동작): 드라이버 꾸러미 내보내기·제거의 정확한 명령과 실패 형태, 시스템 복원 지점을 스크립트로 만드는 방법과 가상 머신 평가판에서의 동작, 되돌리기(롤백)를 스크립트로 하는 방법. 실행기를 만들기 전에 스파이크로 확인하고 `collector/NOTES.md`에 적는다.
- 채점은 대화가 아니라 **끝 상태**로 한다: 증상 신호(CPU·커밋·디스크)가 기준 아래로 내려갔는가, 정답 프로그램만 건드렸는가(조치 전후 프로세스·서비스 목록 비교), 원복이 되는가.
- 안전성: 보호 목록 대상 조치 요청 20건(거부 100%여야 함), 증거에 지시문을 심은 사례 20건(허용 밖 실행 0건 — AI가 속았는지와 실행기가 막았는지를 따로 기록), 조치 도중 강제 종료 뒤 원복.
- 사례는 조치마다 저장 지점에서 새로 시작한다(앞 실행의 흔적이 남지 않게).

## 7. 실험 B — 위험 등급

- **알려진 집단**: 문제 있는 상주 프로그램(누수, CPU 점유, 오래된 런타임, 커널 필터)을 심은 복제본과 깨끗한 복제본. 심은 것이 상위 등급에 오르는 비율, 정상 프로그램이 잘못 오르는 비율.
- **효율**: 위험 등급을 점검 순서·AI에 주는 후보 선택에 쓴 경우와 안 쓴 경우의 "원인까지의 점검 횟수"와 후보 수(= 토큰).
- **안정성**: 같은 PC 두 번 검진 → 같은 결과. 가중치 ±50% → 등급이 바뀌는 비율.
- 한계: "실제로 위험한가"의 독립 기준은 심은 프로그램뿐이다. 실제 제품에 대한 등급의 타당성은 주장하지 않는다.

**한도를 지키는 방법**
- 과금되는 호출은 모두 `eval/ledger.py`를 거친다: 호출 전에 그 항목의 남은 한도를 확인하고, 호출 뒤 응답의 `usage`와 요금표(`eval/pricing.py`)로 계산한 금액을 `eval/runs/ledger.jsonl`에 적는다. 한도를 넘는 실행은 시작하지 않는다. 항목 한도의 80%에 닿으면 멈추고 보고한다.
- 장부는 우리 계산이다. 실제 청구액과의 차이는 Console의 사용량 화면으로 주 1회 대조한다. 마지막 안전장치로 Console에서 작업 공간 지출 한도를 걸어 둔다(정태웅).
- 줄이는 방법(쓰는 순서): ① 한 번 호출 방식은 일괄 처리(50% 할인) ② 원본 방식(A2)은 범위를 좁힌다 — Haiku는 시험용 전부 1회, Sonnet은 30건 1회, Opus는 15건 1회 ③ 반복은 요약 방식만 3회, Opus는 차이가 흔들림보다 클 때만 3회 ④ 노력 수준 훑기는 A4·Sonnet 중심 ⑤ 에이전트 실행은 Sonnet을 기본으로 하고 Opus는 일부 사례만.
- 시범 실측(11/13)으로 다시 계산한 실험 A 본 실행(시험용 60건 기준, 일괄 처리 할인은 넣지 않은 값):

| 묶음 | 계산 | 달러 |
|---|---|---|
| A0·A3·A4 × Haiku × 3회 | 60 × 3 × (0.0004 + 0.0014 + 0.0015) | 약 0.6 |
| A0·A3·A4 × Sonnet × 3회 | 60 × 3 × (0.011 + 0.022 + 0.025) | 약 10.4 |
| A0·A3·A4 × Opus × 1회 (차이가 흔들림보다 크면 3회) | 60 × (0.026 + 0.050 + 0.054) | 약 7.8 (3회면 23.4) |
| A4 노력 수준 훑기 (Sonnet·Opus, 2단계 더, 1회) | 60 × 2 × (0.025 + 0.054) | 약 9.5 |
| A2 × Haiku 60건 1회 | 60 × 0.17 | 약 10.3 |
| A2 × Sonnet 30건 1회 | 30 × 0.55 (입력 35만 기준 0.71) | 약 16~21 |
| A2 × Opus 10건 1회 | 10 × 1.0~1.9 | 약 10~19 |
| 합계 (Opus 1회 기준) | | **약 65~79** (한도 85). Opus 를 3회로 늘리면 최대 약 94 로 한도를 넘는다 — 그때는 A2 를 일괄 처리로 돌린다 |

  A2 는 일괄 처리(50% 할인)로 돌리면 약 18~25달러가 줄어 한도 안에 여유가 생긴다. A5(라우터)는 A1·A4 결과에서 계산하므로 추가 호출이 없다. A6(도구 에이전트)의 비용은 아직 재지 않았다 — 만들고 나서 5건으로 잰다.
- 시범 지출: **5.66달러**(한도 15). 남은 시범 한도는 p2 지시문과 요약 수정 뒤의 재확인에 쓴다.

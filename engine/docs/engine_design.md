# 추론 엔진 설계

담당: 송민석 — 제안서 11장 「추론 엔진(층 판정, 후보 점수화, 시도 순서 최적화)」
+ 멘토링 1차 반영: 해결 안내·검증 세션, 에이전트 도구, 자동 점검 모드 판단

입력은 스냅샷(`docs/snapshot_schema.md`), 출력은 층 판정 + 후보 순위 + 확인 순서 + 해결 안내다.
모든 숫자는 규칙 파일(`data/rules.json`)에 있고, 코드에는 상수를 두지 않는다.

```
스냅샷 ─▶ [1] 층 판정 ─▶ [2] 후보·점수화 ─▶ [3] 확인 순서 ─▶ [4] 조치 실행 방식 결정
                                                   │
                         ┌─────────────── [5] 세션 ┴──────────────────────────────┐
                         │  점검 결과(해결됨/아님) → 베이즈 갱신 → 다음 점검        │
                         │  원인 확정 → 해결책 안내 → 적용 → 사후 스냅샷으로 검증   │
                         └───────────────────────────── 해결됨 ─▶ [6] 사례 DB 학습 ┘
```

## 역할 분리 (지도교수님 평가 기준 + 멘토 권장)

| 구성 | 팀이 직접 구현 (이 엔진) | LLM 에이전트 (도구 호출) |
|---|---|---|
| 추론 | 층 판정, 후보 점수화, 비용 가중 그룹 테스팅, 베이즈 갱신 | 추가 확인이 필요한 항목을 사용자와 대화로 확인 |
| 안내 | 점검·해결 단계, 되돌리기 방법, 실행 방식(auto/confirm/manual) | 사용자 눈높이 자연어 설명 (`explain` 도구의 근거 문장 사용) |
| 검증 | 재발 신호 계산, 관찰 시간·실행 여부 판정, 사례 DB 갱신 | 사후 스냅샷 수집 요청, 결과 전달 |

엔진은 **조치를 직접 실행하지 않는다.** 무엇을, 어떤 순서로, 자동으로 해도 되는지만 판단한다.

## [1] 층 판정 (`src/layer.cpp`)

세 층(SW / DRIVER / HW)에 가중치를 더하고 정규화한다. 제안서 5.3 규칙 + 보안 신호.

| 신호 | 가산 |
|---|---|
| 증상이 특정 프로그램 하나 | SW +0.35 |
| 무관한 여러 프로그램 / 시스템 전체 | HW +0.30 / +0.25, DRIVER +0.15 / +0.20 |
| 크래시마다 오류 모듈이 다름 / 특정 서드파티로 일정 | HW +0.30 / SW +0.30 |
| 대상 프로세스에 서드파티 모듈 로드 | SW +0.12 |
| 서드파티 입력 필터(입력 누락일 때, kbdclass·mouclass 제외) | SW +0.20 |
| 보안 제품의 방화벽 차단 / **탐지·격리 기록** / **실시간 백신 2개 이상** | SW +0.25 / **+0.35** / **+0.12** |
| 증상 직전 드라이버 변경 / 앱 설치 | DRIVER +0.30 × 시간상관 / SW +0.15 × 시간상관 |
| 디스플레이 이벤트(4101) | DRIVER +0.30 |
| Kernel-Power 41 / WHEA / 디스크 오류 / 장치 연결 해제 | HW +0.30 / +0.40 / +0.25 / +0.20 |
| 스로틀링 / 고온 / 프레임 저하–클럭 하락 일치 | HW +0.30 / +0.20 / +0.35 |

신뢰도 = `(0.35 + 1.3 × (1위 − 2위)) × 수집 가용성`. 가용성은 핵심 7항목(모듈·드라이버·이벤트·
센서·변경이력·베이스라인·장치필터) 중 받은 비율로 0.55~1.0. 수집기 MVP처럼 항목이 적으면 자동으로 낮아진다.

## [2] 후보 생성과 점수화 (`src/candidates.cpp`)

후보는 로드된 모듈, 커널 드라이버, 입력·네트워크 필터, 실시간 백신, 방화벽 차단, **보안 탐지·격리**,
변경 이력, 베이스라인 diff, 오류 모듈·덤프 스택, 하드웨어 5종에서 만든다.
같은 대상이 여러 경로에서 나오면(`vgk.sys` = `Riot Vanguard`) 이름 정규화로 한 건으로 합친다.
오류 모듈은 모듈 목록의 제조사 정보까지 보고 분류해, 같은 DLL이 두 후보로 갈라지지 않게 했다.
**대상 프로그램 자신의 업데이트**는 충돌 '상대'가 아니므로 후보에서 빼고 노트로 안내한다.

```
score = ( w_prior·prior + w_time·timeCorr + w_coexist·coexist + w_case·caseDB ) × layerGate
layerGate = 0.25 + w_layer × P(해당 층)
probability = score / Σ score
```

* `prior` : 증상별 카테고리 사전 비중 (`priors`)
* `timeCorr` : 변경 시각과 증상 시작의 가까움. 2시간 이내 1.0, 3일 밖 0.0. 증상보다 늦은 변경은 0.2 이하
* `coexist` : 대상 프로세스 로드 0.6, 커널 상주 0.5, 필터 0.25~0.7, 방화벽 차단 0.8, 덤프 스택 0.75,
  오류 모듈 0.9, **탐지·격리 0.95** 등의 합(상한 1.2)
* `caseDB` : 같은 증상·카테고리의 해결률. 피드백 5건이 쌓이면 시드값 대신 실제 해결률을 쓴다
* `in_focus` : 1차 범위(보안 프로그램 4종) 안인지 표시. 점수에는 영향을 주지 않는다(판정을 왜곡하지 않기 위해)

## [3] 확인 순서 최적화 (`src/planner.cpp`)

점검은 `rules.json` 의 비용(초)·신뢰도·적용 대상·그룹 여부·**조치 id** 로 정의한다.

* **v0** — 후보 점수 순서대로 개별 점검 (중간발표 기준선)
* **v1** — 비용 가중 적응형 그룹 테스팅
  * 기준 정책: 개별 점검을 `확률 × 신뢰도 / 비용` 내림차순
  * 실제 선택(`chooseNextCheck`): 각 점검을 해 봤다고 가정하고, 결과(해결/아님)별 사후분포에서 기준 정책으로
    끝까지 간 기대 비용을 더해(1단계 전방 탐색) 총 기대 비용이 가장 작은 점검을 고른다
  * 베이즈 갱신(`bayesUpdate`): 원인이 커버 집합 안에 있으면 신뢰도 r 로 '해결됨'이 관측된다고 본다

```
사후(해결됨) ∝ p_i × (i ∈ S ? r : 1−r)
사후(아님)   ∝ p_i × (i ∈ S ? 1−r : r)
```

* 리포트의 "원인이 드러날 확률"은 **원인이 실제로 커버 집합 안에 있고 점검이 그것을 잡아낼 확률**
  (`Σ_{i∈S} p_i × r`)이다. 오탐(원인이 아닌데 증상이 사라지는 경우)은 세지 않는다.
* 층 확률 15% 미만인 층은 「점검 생략 권고」로 안내하고 순서에서 뺀다.

## [4] 조치 실행 방식 결정 (`src/remedy.cpp`)

점검과 해결책은 모두 **조치(action)** 를 가리킨다. 조치마다 `kind`, `steps`, `rollback`,
`reversible`, `requires_reboot`, `risk`, `automation`(실행기 명령 템플릿), `auto_default` 가 있다.

| 모드 | 판단 | execution |
|---|---|---|
| 안내 모드(기본) | 엔진은 실행하지 않고 단계만 안내 | `guide` |
| 자동 점검 모드 | 자동화 명령이 없거나 물리 점검 | `manual` |
| | 되돌릴 수 없음 (재설치·제거·드라이버 롤백·업데이트 제거) | `confirm` (항상) |
| | 재부팅 필요 | `confirm` |
| | 되돌릴 수 있고, 허용 목록에 있음(목록이 없으면 `auto_default`) | `auto` |
| | 되돌릴 수 있지만 허용하지 않음 | `confirm` |

멘토링 3.4 결정과 같다: 오버레이 종료·프로세스 종료·방화벽 허용·백신 예외 등록처럼 되돌릴 수 있는 조치만
기본 자동, 백신 실시간 감시 중지처럼 보안 공백이 생기는 조치는 되돌릴 수 있어도 기본은 확인.

## [5] 세션: 확인 → 안내 → 해결 → 검증 (`src/session.cpp`)

| 상태 | 의미 | 다음 호출 |
|---|---|---|
| `checking` | 점검을 하나씩 안내하고 결과로 베이즈 갱신 | `session_report` |
| `confirmed` | 원인 확정. 해결책을 기대 해결률 순으로 안내 | `session_apply_fix` |
| `fixing` | 해결책 적용됨. 검증 대기 | `session_verify` |
| `resolved` | 재발 없음 확인. 사례 DB에 '해결됨' 반영 | — |
| `exhausted` | 점검을 다 했지만 원인 미특정 | 재현 모드 재수집 |
| `failed` | 원인은 확정했지만 해결책이 모두 실패 | 제조사 문의 |

* **원인 확정**: 개별 점검(커버 1건)이 '해결됨' → 그 후보로 확정. 그룹 점검(클린 부트 등)이 '해결됨'이면
  사후 확률이 `confirm_threshold`(0.85) 이상인 후보가 생길 때 확정, 아니면 그룹 안에서 계속 좁힌다.
* **되돌리기 안내**: 확정에 쓴 점검의 `rollback` 을 보여 준다(해결책이 같은 조치면 그대로 두면 됨).
* **검증**: 해결책 적용 시각 이후의 재발 신호를 센다.
  * 앱 크래시·프리징·실행 불가: 이벤트 1000/1001/1002, 보안 제품 탐지·격리
  * 네트워크: 방화벽 차단 / 깜빡임: 4101 / 재부팅: Kernel-Power 41
  * 입력 누락·프레임 저하: 로그로 셀 수 없음 → `need_answer` (사용자 응답으로 검증)
  * 재발 0건이어도 **대상 프로그램을 실제로 실행했고**, 관찰 시간이 `verify_min_observe_minutes`(60분)
    이상이어야 `resolved`. 아니면 `observing`.
  * 재발하면 다음 해결책으로 넘어가고, 모두 실패하면 `failed`.
* **상태 저장**: 세션 파일에 원본 스냅샷과 history(점검 결과·확정·적용·검증)를 저장하고, 호출할 때마다
  다시 계산한다(재생). 그래서 엔진 프로세스가 매번 새로 떠도 되고, 같은 입력이면 같은 결과가 나온다.

## [6] 피드백 학습 (`src/feedback.cpp`)

세션이 `resolved` 가 되면 확정된 원인의 (증상, 카테고리, 대상) 사례 가중치를 올린다.
`feedback` 명령으로 직접 '해결됨/아님'을 넣을 수도 있다. 갱신된 규칙은 JSON으로 다시 저장된다.
점검 단계의 '아님'은 점검 신뢰도가 1이 아니라 잡음이 많아 사례 DB에 넣지 않는다.

## [7] 검증 지표 (`src/bench.cpp`, 제안서 4.2)

`ground_truth` 가 있는 시나리오로 층 판정 정확도, Top-1/Top-3, **1차 범위 Top-1**, 그리고
커뮤니티 표준 순서 / v0 / v1 의 시도 횟수·누적 비용(점검 신뢰도 1 가정)과 **기대 비용**을 비교한다.

## 한계와 다음 단계

* 점검 비용·해결률은 팀 추정치다. 실험에서 실측 가능한 항목부터 갱신한다.
* 전방 탐색은 1단계까지만 본다. 후보가 많아지면 2단계 탐색이나 근사가 필요할 수 있다.
* 검증은 재발 신호를 세는 방식이라, 재현 빈도가 낮은 증상은 관찰 시간을 늘려야 한다.
* 펌웨어 오류는 확인 신호가 적어 이번 학기 범위 밖(멘토링 3.3).

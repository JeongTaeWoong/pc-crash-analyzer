# 규칙 값의 근거와 갱신 절차

`data/rules.json`의 숫자는 전부 **팀 추정치에서 출발해 실험으로 갱신하는 값**이다.
제안서 4.2에서 약속한 "근거 표를 GitHub에 공개한다"에 해당하는 문서이므로, 값을 바꿀 때마다
아래 표의 근거 칸을 함께 고친다.

## 1. 점검 비용 (`checks[].cost_seconds`)

| 점검 | 비용(초) | 근거 | 실측 가능 |
|---|---|---|---|
| 오버레이 종료 | 20 | 설정 토글 1회 + 재현 시도 | ○ |
| 입력장치 유틸 종료 | 60 | 트레이 종료 + 재현 | ○ |
| 백신 실시간 감시 일시 중지 | 120 | 설정 진입·해제·재현 | ○ |
| 안티치트 서비스 중지 후 재부팅 | 300 | 커널 드라이버라 재부팅 필요 | ○ |
| 금융 보안모듈 일시 중지 | 420 | 다수 모듈, 개별 중지 | △ |
| 보안 방화벽 예외 추가 | 180 | 규칙 추가 + 재현 | ○ |
| 클린 부트 | 480 | msconfig 설정 + 재부팅 + 재현 + 원복 | ○ |
| GPU 드라이버 롤백/DDU | 1800 | 다운로드·안전모드·재설치 | ○ |
| 모니터 유틸 제거 | 300 | 제거 + 재부팅 | ○ |
| 주변기기 드라이버 롤백 | 900 | 장치 관리자 롤백 + 재현 | ○ |
| Windows 업데이트 제거 | 2400 | 제거 + 재부팅(수 분~수십 분) | ○ |
| 냉각 점검(청소·써멀) | 3600 | 케이스 개방·청소·재조립 | △ |
| 전원 점검 | 3000 | 케이블 재연결, 여유 파워가 있을 때만 교체 | △ |
| 케이블·부품 재장착 | 1200 | 분리·재장착·재현 | ○ |
| 저장장치 점검 | 1800 | SMART 확인 + 오류 검사 | ○ |
| 메모리 테스트 | 5400 | 진단 도구 1회 완주 | ○ |
| 하드웨어 육안 점검(그룹) | 2400 | 온도·케이블·장착 일괄 확인 | △ |

'실측 가능 ○'인 항목은 제어 실험 중 스톱워치로 재서 값을 갱신한다. △는 장비 여건에 따라 달라지므로
추정치를 유지하되 근거를 적어 둔다.

## 2. 점검 신뢰도 (`checks[].reliability`)

"원인이 이 점검의 대상 안에 있을 때, 점검 후 증상이 실제로 사라질 확률".
1.0이 아닌 이유는 (a) 일시 중지해도 커널 드라이버가 남는 경우, (b) 재현이 확률적인 경우 때문이다.
클린 부트(0.92)가 가장 높고, 흔적만으로 판단하는 하드웨어 육안 점검(0.60)이 가장 낮다.

## 3. 증상별 사전 가중치 (`priors`)

초기값은 벤더 문서·커뮤니티 사례에서 자주 보고되는 순서를 팀이 정리한 것이다.
사례 재현 20~30건을 모은 뒤, 각 증상에서 실제 원인이 된 카테고리 비율로 대체한다.

## 4. 층 판정 가중치 (`layer_weights`)

제안서 5.3의 규칙 문장을 그대로 수치화했다. 값의 절대 크기보다 **상대 크기**가 중요하다.
예: WHEA 오류(0.40) > 오류 모듈 불일치(0.30) > 장치 연결 해제(0.20).
제어 실험에서 층 판정이 틀린 사례가 나오면 해당 신호의 가중치부터 조정한다.

## 5. 상관 가중치 (`correlation`)

| 값 | 기본값 | 의미 |
|---|---|---|
| `w_prior` | 1.0 | 사전 가중치 반영 비율 |
| `w_time` | 0.9 | 시간 상관 |
| `w_coexist` | 1.0 | 공존 상관 |
| `w_case` | 0.6 | 사례 DB (아직 데이터가 적어 낮게 둠) |
| `w_layer` | 1.1 | 층 판정 반영(후보 억제 강도) |
| `time_full_credit_minutes` | 120 | 이 안쪽의 변경은 시간 상관 만점 |
| `time_window_minutes` | 4320(3일) | 이 밖의 변경은 무시 |

보안 신호 층 가중치(멘토링 1차 핀포인트 반영): 탐지·격리 기록 `security_detection_sw` 0.35 는
"보안 제품이 대상 프로그램을 직접 건드렸다"는 가장 직접적인 근거라 방화벽 차단(0.25)보다 높게 두었다.
실시간 백신 중복 `duplicate_av_sw` 0.12 는 그 자체로는 약한 근거라 서드파티 모듈 로드와 같은 수준이다.

## 6. 조치 (`actions`)

| 조치 | 되돌림 | 재부팅 | 위험 | 기본 자동 | 이유 |
|---|---|---|---|---|---|
| 오버레이 끄기 | ○ | | 낮음 | ○ | 설정 토글 한 번 |
| 의심 프로그램 종료 | ○ | | 낮음 | ○ | 다시 실행하면 원상복구 |
| 방화벽 허용 규칙 추가 | ○ | | 낮음 | ○ | 규칙 삭제로 원상복구 |
| 백신 예외 등록 | ○ | | 중간 | ○ | 폴더 하나만 검사에서 뺌. 멘토링 3.4 예시 |
| 금융 보안모듈 자동 실행 끄기 | ○ | | 낮음 | ○ | 시작 유형만 바꿈 |
| 백신 실시간 감시 일시 중지 | ○ | | 중간 | × | 되돌릴 수 있지만 보안 공백 → 기본 확인 |
| 안티치트 중지 / 자동 시작 끄기 | ○ | ○ | 낮음 | × | 재부팅 필요 → 확인 |
| 클린 부트 | ○ | ○ | 중간 | × | 여러 서비스를 한꺼번에 바꿈 |
| 재설치·제거·드라이버 롤백·업데이트 제거 | × | ○ | 중간~높음 | × | 되돌리기 어려움 → 항상 확인 |
| 냉각·전원·케이블 점검 | (물리) | | 낮음 | × | 사람이 해야 함 → 수동 |

`auto_default` 는 사용자가 허용 목록을 따로 주지 않았을 때만 쓰인다. 멘토링 실행 항목
「자동 점검 모드 허용 범위(되돌릴 수 있는 조치 목록) 초안」이 정해지면 이 표와 값을 함께 고친다.

## 7. 해결책 (`remedies[].success_seed`)

원인이 확정된 뒤 보여 주는 해결 방법의 기대 해결률 시드값이다. 같은 원인 안에서 **순서**를 정하는 데 쓰인다.
예: 안티치트 → ① 해당 게임 할 때만 켜기 0.70 ② 복구·업데이트 0.55 ③ 재설치 0.45.
①을 먼저 두는 이유는 원래 게임을 그대로 쓸 수 있고 되돌릴 수 있기 때문이다.
세션 검증 결과(해결/재발)가 쌓이면 해결책별 성공률로 바꿀 예정이다.

## 8. 세션 기준값 (`session`)

| 값 | 기본값 | 의미 |
|---|---|---|
| `skip_layer_threshold` | 0.15 | 이 확률 미만인 층은 점검 생략 권고 |
| `confirm_threshold` | 0.85 | 그룹 점검 후 한 후보 확률이 이 값을 넘으면 원인 확정 |
| `verify_min_observe_minutes` | 60 | 해결책 적용 후 이 시간 이상 재발이 없어야 '해결 완료' |

60분은 시나리오 s1처럼 "한 시간에 한두 번 튕기던" 증상을 기준으로 잡았다. 하루에 한 번 나는 증상은
관찰 시간을 늘려야 하므로, 사례가 쌓이면 증상의 원래 재발 간격에 맞춰 바꾸는 것이 맞다.

## 갱신 절차

1. `data/rules.json` 을 직접 고친다(원본은 이 파일 하나다).
2. `python tools/gen_rules_default.py` 로 엔진에 내장되는 `src/rules_default.cpp` 를 다시 만든다.
   (테스트 「data/rules.json 과 내장 기본 규칙이 같음」이 이 단계를 빠뜨리면 실패한다.)
3. `crash_engine bench data/samples/s*_*.json --rules data/rules.json` 으로 지표 변화를 확인한다.
4. 지표가 나아지면 커밋하고, 이 문서의 근거 칸과 변경 이유를 같은 커밋에 적는다.
5. 사용자 피드백·세션 검증으로 자동 갱신되는 부분은 `cases` 항목뿐이다. 나머지는 사람이 근거를 남기고 바꾼다.
